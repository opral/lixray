# 1 TiB media workspace qualification

## Release envelope

The release workload is one deterministic 1 TiB workspace with 10,000 files,
2,000 media files, a 20 GiB maximum file, 5,000 commits, one to three active
users, and two concurrent 100 Mbit/s proxy reads. It includes proxies,
production audio, graphics, project metadata, selected originals, review
exports, and current masters. Regenerable caches and complete camera archives
are outside the target.

The canonical manifest is generated by `perf/movie/corpus.mjs`. Payload bytes
come from `perf/movie/payload.mjs`, which can reproduce an arbitrary range
without materializing the file or a second fixture tree.

The remote qualification runner materializes that manifest in byte-balanced
segments so each invocation remains inside CI's execution ceiling. Each media
file uses a bounded window of four concurrent 16 MiB parts. Segments
must run sequentially against one fresh workspace; the last segment extends
the resulting history to exactly 5,000 commits and verifies the final count:

```sh
LIXRAY_INTERNAL_TOKEN=... pnpm perf:movie:remote -- \
  --url https://lix-server.example \
  --workspace perf-movie-1tib-REVISION \
  --segment-index 0 \
  --segment-count 4 \
  --finalize-history false
```

Pass `--finalize-history true` only for the final segment. Use a fresh
workspace and run each segment exactly once. The runner retries an acknowledged
16 MiB media part in place and writes one JSON report per segment under
`perf/results/`.

The manual GitHub workflow first promotes the immutable `sha-*` image produced
by the merge's server-image job and waits for its health check. This keeps the
qualification independent of the separately coordinated web release and
guarantees every segment runs the tested engine revision.

## API hard cut

Keep one file resource. Do not add separate multipart, range, media, and
ordinary-file API families.

```text
GET /lix/v1/file?path=...              # complete or one forward Range
POST /lix/v1/file/upsert?path=...       # complete small file or one media part
```

For a media part, `POST` carries a client-generated `Lix-Upload-Id` and
`Content-Range: bytes start-end/total`. Parts are fixed at 16 MiB except the
last, with up to four aligned parts in flight. An incomplete write returns
`308` plus the acknowledged contiguous `Range`; the final contiguous window
atomically publishes one new file version and returns the ordinary mutation
receipt. Replaying an acknowledged part is idempotent. Multipart responses,
suffix reads, unknown final lengths, and server-side composition are outside
the 90% path.

This uses the proven parts-then-atomic-publication model without inheriting its
full API surface. S3 documents independent retryable parts followed by one
completion operation, while Google Cloud Storage documents sequential
`Content-Range` requests and a `308` response containing the acknowledged
offset:

- <https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html>
- <https://docs.cloud.google.com/storage/docs/performing-resumable-uploads>

## Storage invariants

- Each request and storage transaction is bounded by the 16 MiB part, not the
  complete file.
- Complete fixed-size CAS chunks are durable before the upload offset is
  acknowledged.
- Durable upload state records the path and total length. One manifest leaf
  stores all chunk receipts for each completed 16 MiB part. Restart derives
  contiguous progress from those leaves without per-chunk journal rows.
- The final part durably completes the immutable manifest, then the ordinary
  file transaction publishes its blob reference, filesystem rows, history,
  and commit atomically. Staged CAS objects have no logical file path and are
  invisible until publication succeeds.
- A media blob uses a domain-separated Merkle identity over total length and
  ordered `(chunk hash, chunk length)` pairs. This preserves exact-file and
  exact-chunk deduplication without rereading 20 GiB to calculate a flat hash.
- Ordinary small-file writes keep their direct complete-blob path. Both paths
  publish the same `lix_file` abstraction.
- Abandoned immutable chunks are safe and reclaimed by later GC. Immediate
  abort cleanup is outside the happy path.

## Qualification gates

- Peak incremental server RSS stays below 512 MiB during one 20 GiB upload and
  two proxy reads.
- Large-file ingest reaches at least 70% of the same backend's direct payload
  throughput.
- A killed process resumes an upload at the last acknowledged part and never
  exposes a partial file.
- Random ranges reproduce the deterministic source on RocksDB and SlateDB.
- Two concurrent 100 Mbit/s reads complete without falling behind their
  pacing schedule.
- Project-save p95 remains below 500 ms during playback and media ingest.
- Identical imports, renames, and branches add no duplicate payload rows.
- Current and historical file digests match after restart and restore on both
  backends.

## Measured baseline

The whole-buffer direct CAS path peaks at 1,101,944 KiB RSS for one 256 MiB
RocksDB write and 904,348 KiB for SlateDB. Equivalent 1 MiB process runs peak
at 60,192 KiB and 62,692 KiB respectively, yielding roughly 3.97x and 3.21x
incremental payload amplification before HTTP buffering. See `FINDINGS.md`.
Raising the 64 MiB request ceiling is therefore explicitly disqualified as a
solution.

The fixed-chunk resumable implementation reverses that scaling. With payload
accounting scans excluded from process RSS, a combined 256 MiB then 1 GiB
write peaks at 243,780 KiB on RocksDB and 113,216 KiB on SlateDB. The 1 GiB
write completes in 1.29 s and 0.78 s respectively. This qualifies the
architecture. After removing redundant CAS compression and automatic RocksDB
live-blob relocation, the exact 20 GiB run completes in 22.51 s on RocksDB
with 248,324 KiB RSS and in 13.92 s on SlateDB. Equivalent raw adapter controls
take 21.52 s and 11.58 s, so Lix retains 95.6% and 83.2% of backend throughput.

The interference qualification now passes locally on both backends after
seeding the target 5,000-commit project history. It runs two paced 100 Mbit/s
range streams with one second of playback read-ahead during a 512 MiB ingest
and 40 project saves. RocksDB has zero late reads, 1.51 ms save p95, and 800.9
MiB/s ingest; SlateDB has zero late reads, 6.66 ms save p95, and 1,223.3 MiB/s
ingest.
